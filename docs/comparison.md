# Сравнение с apt

Проверка выполнена 1 ноября 2026 года на индексе Ubuntu noble, компонент
`main`, архитектура `amd64`. Версия эталонного инструмента:
`apt 2.8.3 (amd64)`.

Источник индекса:

```text
https://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/Packages.xz
```

SHA256 загруженного `Packages.xz`:

```text
2a6a199e1031a5c279cb346646d594993f35b1c03dd4a82aaa0323980dd92451
```

Программа получает зависимости самостоятельным разбором метаданных.
Команды apt используются только отдельным скриптом сравнения и не вызываются
из приложения.

## Повторение проверки

Из корня проекта в Linux, где доступны `apt-cache` и `apt-get`:

```sh
PYTHONPATH=src python3 tools/compare_apt.py --depth 3
```

Скрипт один раз загружает индекс в `.cache/apt-reference/Packages.xz`.
Анализатор и apt читают одни и те же распакованные данные. Для apt создаются
отдельные списки пакетов, кеши, список источников и пустой файл состояния
установленных пакетов. Источники и настройки предпочтений основной системы
не используются. Установка пакетов и `apt-get update` не выполняются.

Для частного источника сравнения используется `trusted=yes`: эксперимент
сопоставляет содержимое одного индекса, но не проверяет подпись архива.
SHA256 фиксирует использованные байты. При повторном запуске сохраняется
тот же кеш; при загрузке нового снимка его хеш и результаты могут измениться.

В `output/comparison/` создаются:

- `report.json` — версии, размеры графов и обнаруженные различия;
- `*.dot` — вывод `apt-cache dotty`;
- `*.depends.txt` — прямые обязательные зависимости из `apt-cache depends`;
- `*.simulation.txt` — результат симуляции установки;
- `*.uris.txt` — план получения архивов без их скачивания.

Кеши и результаты генерируются при запуске и исключены из Git.

## Граф зависимостей

Глубина корня равна нулю. В эксперименте установлен предел 3. В сравнении
рёбер учитываются только узлы, раскрытые анализатором; исходящие рёбра
граничных узлов не сравниваются.

| Пакет | Версия | Узлы | Рёбра | Только у анализатора | Только у apt |
|---|---|---:|---:|---:|---:|
| `hello` | `2.10-3build1` | 4 | 4 | 0 | 0 |
| `make` | `4.3-4.1build2` | 4 | 4 | 0 | 0 |
| `gzip` | `1.12-1ubuntu3` | 14 | 23 | 0 | 1 |

Для `hello` и `make` обязательные рёбра совпали. У `gzip` apt показывает
обе альтернативы `dpkg | install-info`, а анализатор выбирает первую
доступную — `dpkg`. Поэтому в исходном графе apt есть дополнительное ребро
`gzip → install-info`. В симуляции apt тоже выбрал `dpkg`.

Прямые зависимости:

| Пакет | Анализатор | Объявленные apt варианты |
|---|---|---|
| `hello` | `libc6` | `libc6` |
| `make` | `libc6` | `libc6` |
| `gzip` | `libc6`, `dpkg` | `libc6`, `dpkg`, `install-info` |

`apt-cache dotty` дополнительно выводит отношения `Conflicts` и `Breaks`,
которые не относятся к графу обязательных зависимостей. Для раскрытых узлов
получено соответственно 19, 18 и 26 таких рёбер. Они не считались ошибками
анализатора. В DOT сравниваются обычные рёбра и синие `Pre-Depends`, а
дополнительные цветные отношения учитываются отдельно.

## Порядок загрузки

В приложении этот термин означает порядок «зависимости перед зависимым
пакетом» для показанного графа. Для графа без циклов он получается при
завершении итеративного DFS. Порядок относится только к раскрытой части
графа, если задано ограничение глубины.

Во всех трёх реальных примерах обнаружен цикл:

```text
libc6 → libgcc-s1 → libc6
```

Строгого линейного порядка для этого цикла нет. Приложение сообщает об этом,
а не выводит произвольный список под видом корректной сортировки.

Эталонные команды, которые запускает скрипт с отдельными путями состояния:

```sh
apt-get -s --no-install-recommends install hello=2.10-3build1
apt-get --print-uris --download-only --yes --no-install-recommends \
    install hello=2.10-3build1
```

Вывод `-s` описывает операции распаковки `Inst` и настройки `Conf`.
Он не является журналом сетевого скачивания. Вывод `--print-uris`
содержит план получения архивов; фактические сетевые моменты завершения
загрузки этим экспериментом не измеряются.

План URI и порядок `Inst` в полученных результатах совпали:

- `hello`: `gcc-14-base`, `libgcc-s1`, `libc6`, `hello`;
- `make`: `gcc-14-base`, `libgcc-s1`, `libc6`, `make`;
- `gzip`: `gcc-14-base`, `libc6`, `libgcc-s1`, `libbz2-1.0`, `liblzma5`,
  `libmd0`, `libpcre2-8-0`, `libselinux1`, `libzstd1`, `zlib1g`,
  `libacl1`, `tar`, `dpkg`, `gzip`.

Во всех случаях множество запланированных apt пакетов совпало с множеством
узлов построенного графа. Это результат данных трёх примеров, а не гарантия
для произвольного репозитория.

apt может устанавливать пакеты цикла с промежуточными ненастроенными
состояниями. Поэтому наличие у apt практического плана операций не означает,
что у графа существует строгая сортировка всех зависимостей.

Для проверки успешного случая отдельно запущен пакет без зависимостей:

```sh
PYTHONPATH=src python3 tools/compare_apt.py netbase \
    --output output/comparison-netbase
```

Получена версия `netbase=6.4`: один узел, ноль рёбер обязательных
зависимостей. Анализатор вернул порядок `netbase`. План URI и симуляция apt
тоже содержат только `netbase`. Граф без цикла и с несколькими узлами
дополнительно проверяется на тестовом репозитории и в автоматических тестах.

## Границы сравнения

Используется один индекс `noble/main/amd64`, без обновлений, других
компонентов и уже установленных пакетов. Рекомендации отключены.
Анализатор выбирает альтернативы и версии локально и детерминированно;
полный решатель конфликтов и совместимости apt он не воспроизводит.

`dotty` строится для кандидата apt, поэтому в эксперименте берутся версии
кандидатов из того же индекса. Для произвольной старой версии корня
нельзя автоматически считать вывод `dotty имя` эталоном её зависимостей.

Справка по использованным инструментам:

- [apt-cache](https://manpages.debian.org/trixie/apt/apt-cache.8.en.html)
- [apt-get](https://manpages.debian.org/unstable/apt/apt-get.8.en.html)
